| D28 | Delivery timing is classified by the LLM into explicit / relative / urgency / none (with evidence + reasoning). | D29 | "Never invent": only explicit and resolvable-relative timeframes yield a PO date. | D30 | The PO is a document in the **transaction currency** (the supplier/quote currency): `total` = sum of the line items in that currency, so it reconciles with the ERP's own sum. The CHF conversion stays internal to approval routing and is never the PO total. A PO's document total belongs in its transaction currency, with group currency for approvals | Convert every line to CHF (per-line rounding drifts from the single end-rounding, D19); keep sending the CHF total (inconsistent) |
| D31 | `gl_account` is left for the ERP to derive (account determination); we do not assign one | Refined by D33 | The master data has a GL list but no determination rule (no cost-centre/material→GL mapping), and the mock API itself documents GL as "derived by account determination, not entered by the buyer". Assigning one would be inventing business data (prompt rule 6). The advisory warning is expected | Guess a GL from the item text (accounting risk); map arbitrarily from the GL list |
| D32 | An explicitly **flexible** request (delivery kind=urgency, urgency=low — "whenever you can", "no rush") is satisfied with a standard lead time (`thresholds.defaultDeliveryLeadDays`, default 14) rather than a clarification round-trip; `basis="default"`. High/normal urgency and silence still never get a default | Decided | "Whenever you can" is the requester delegating the date to us, so applying a documented lead time honours them rather than inventing against their wishes (cf. D29). Asking a requester who already said "no rush" to name a date is pointless friction. High-urgency must not be auto-defaulted — a standard lead time could be far too slow, and that is the costly case to get wrong | Keep asking for every missing date (friction); auto-default every urgency level (risks under-serving urgent orders); default on silence too (silence ≠ flexible) |
| D33 | GL account is determined by content (refines D31): the LLM infers a generic purchasing category (`category_hint`, e.g. "packaging"), kept customer-neutral in the prompt; code fuzzy-matches it to `gl_accounts` (`resolveGlAccount`, same pattern as supplier/cost-centre). It is sent **only on an unambiguous match** (`match && !ambiguous`); otherwise left blank for ERP determination | Decided | The GL list is category-based, so content-based determination is feasible and silences the advisory for clear cases, while the unambiguous gate avoids a mis-posting on a guess. Keeping the category generic in the prompt (not GL codes) keeps the prompt provider- and customer-neutral; the customer's GL list stays in master data | LLM emits the GL code directly (bakes customer master into the prompt; unauditable); send the best match regardless of ambiguity (mis-posting risk); keep leaving it entirely to the ERP (D31 — but the clear cases are safe to fill) |

## Assumptions about the spec

Fill these in as they are resolved. Reference the number in code comments and commit messages.

| # | Question | Current default | Status |
|---|---|---|---|
| A1 | The approval table has gaps between ranges (e.g. 1,000.50 is neither ≤1,000 nor ≥1,001). Which band applies? | Anything above a band's upper limit moves to the next band (so 1,000.01 requires the second band) | Decided (D18) |
| A2 | Does the CHF total include VAT, shipping and discounts? | No VAT adjustment is applied. The system takes line-item prices as stated in the email or PDF (ex-VAT, ex-shipping). If the quote separates out VAT or a discount, those lines would be extracted and included as ordinary line items. A real deployment must confirm whether the ERP expects ex-VAT or inc-VAT totals; if inc-VAT, every CHF total and approval band is understated by the VAT rate. | Decided |
| A3 | Which FX rate and rounding rule apply? | Rate from `master_data.json`; total rounded to 2 dp at the end (not per-line) | Decided (D19) |
| A4 | When information is missing, should the system draft a reply to the requester or only flag it? | Both: `needs_clarification` status includes a `draftReply` the clerk can send; `needs_human_review` flags for the clerk without a draft (unclear what to ask) | Decided |
| A5 | Is the PO created before or after approvals are collected? | Before: the mock API creates the PO immediately on submission. The approval chain is computed to route the requisition, but collecting approvers' responses is outside the take-home scope (no approval inbox modelled). | Decided |
| A6 | Requester equals approver, or one person holds two approval roles | Requester-as-approver → keep the step, flag it `requiresAlternate`, route to needs_human_review (D27). Duplicate roles for one person collapse to a single step, promoted to the higher role | Decided (D27) |
| A7 | What happens with duplicate requisitions (same email, forwarded twice)? | Idempotent on message-ID: the same unmodified email never creates two POs. Known limitation: a forwarded copy has different headers, so its hash differs and can produce a second PO. There is no cross-requisition deduplication; an operator must detect this from the subject and supplier. | Decided |
| A8 | How should vague or relative delivery timing be handled when no explicit date is given? | Classify (explicit/relative/urgency/none); resolve explicit + relative to a concrete date deterministically; a flexible/low-urgency request gets the standard lead time (D32); high-urgency and silence never get a date → clarification (D28, D29, D32) | Decided (D28/D29/D32) |
| A9 | Can a PO go through with partial approvals? | No — unanimous approval is required. If any reviewer rejects, the PO is rejected. A single pending response is enough to keep the requisition in "waiting for approval". | Decided |
| A10 | Does a blocked supplier prevent the clerk from submitting for approval? | No — the system flags the supplier as blocked (chip turns red, warning shown) but does not lock the form. The clerk can override and submit; the approvers then decide. | Decided |
| A11 | Cost centre is mandatory: without a resolved cost centre the approval chain cannot be determined. | The clerk form enforces this — the submit button stays disabled until a valid cost centre is selected from the master-data list. | Decided |
| A12 | Can a requisition in "Waiting for Approval" be recalled and edited? | Out of scope for the take-home. Once submitted, the approval state is read-only. In production: add a Recall action that resets the status to `needs_human_review`, preserving the audit trail, so the clerk can correct fields and resubmit. | Known limitation |
| A13 | What happens when a requester sends a correction email ("ignore my last email, quantity is 12 not 120")? | If the correction's `In-Reply-To` header matches an existing unsubmitted requisition, the pipeline overwrites that row in place, re-runs extraction with a correction note to the LLM, and re-runs all downstream stages (resolve, approve, decide). The same `REQ-xxx` reference is preserved. If the original PO was already submitted before the correction arrived, the correction is treated as a new independent requisition and the clerk handles the discrepancy manually — recalling a submitted PO is out of scope (see A12). | Decided |
