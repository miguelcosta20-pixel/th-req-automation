| D26 | Eval scoring (label schema, per-field checks, run, aggregate) lives in `src/eval-core.ts`, imported by the CLI (`src/eval.ts`) | Decided | Keeps `src/eval.ts` small and the checks testable in isolation. (Originally shared with a Quality UI screen, dropped with D22 — the CLI → `docs/eval.md` is the evaluation story) | Inlining all of it in `src/eval.ts` |
| D27 | Self-approval (supersedes D20): if the requester is one of the required approvers, keep that step, flag it `requiresAlternate`, and route to **needs_human_review** — never auto-resolve by dropping them, even if a more senior approver could cover the band | Decided | The old coverage rule silently produced short chains (e.g. a band-4 requisition with 3 approvers) and could let a requisition proceed without the owner's independent sign-off. A requester must never approve their own request; a person must decide the alternate (A6) | Keep dropping the requester when a higher role covers (D20); reject outright; auto-substitute a deputy (no deputy data modelled) |
| D28 | Delivery timing is classified by the LLM into explicit / relative / urgency / none (with evidence + reasoning). The LLM may resolve a relative phrase to an ISO date (it can read "Bis Ende Mai" / calendar context the code parser cannot); deterministic code (`src/delivery.ts`) then validates that date — well-formed ISO and not before the email send date — and uses it, else falls back to its own offset parser anchored on the email date. urgency / none → no date | Decided | Accept vague-but-sufficient requests instead of demanding an explicit date, while a deterministic guardrail (validity + non-past check + parser fallback) keeps the LLM's date resolution honest and auditable | LLM date with no code check (risks hallucinated/garbage dates); code-only parser (misses non-English / calendar-boundary phrases); keep requiring an explicit date |
| D29 | "Never invent": only explicit and resolvable-relative timeframes yield a PO date. Pure urgency ("ASAP", low stock) and silence yield no date → clarification (prioritised when urgency is high). Unparseable relative phrases also fall through to clarification | Decided | SAP requires a delivery date; fabricating one for a vague request risks committing the supplier to a date nobody agreed to. Clarification is the safe action when no date is genuinely derivable | Guess a date from urgency; apply an arbitrary default |
| D30 | The PO is a document in the **transaction currency** (the supplier/quote currency): `total` = sum of the line items in that currency, so it reconciles with the ERP's own sum. The CHF conversion stays internal to approval routing and is never the PO total. Line `unit_price` is the effective per-unit price (the per_100 basis applied), and `item_code` is extracted and sent when a line states a part/material number — else left null (a genuinely free-text line) | Decided | The ERP warned `total != sum(lines)` because we sent a CHF total with original-currency lines (the ratio was exactly the FX rate); and per_100 lines double-counted. A PO's document total belongs in its transaction currency, with group currency for approvals | Convert every line to CHF (per-line rounding drifts from the single end-rounding, D19); keep sending the CHF total (inconsistent) |
| D31 | `gl_account` is left for the ERP to derive (account determination); we do not assign one | Decided | The master data has a GL list but no determination rule (no cost-centre/material→GL mapping), and the mock API itself documents GL as "derived by account determination, not entered by the buyer". Assigning one would be inventing business data (prompt rule 6). The advisory warning is expected | Guess a GL from the item text (accounting risk); map arbitrarily from the GL list |

| A8 | How should vague or relative delivery timing be handled when no explicit date is given? | Classify (explicit/relative/urgency/none); resolve explicit + relative to a concrete date deterministically; never invent for urgency/none → clarification (D28, D29) | Decided (D28/D29) |
| A7 | What happens with duplicate requisitions (same email, forwarded twice)? | Idempotent: the same email never creates two POs | Proposed |
